🚀 [HITO 1] Lanzamiento de la Evaluación N°3: Proyecto End-to-End Profesional
Estimados y estimadas estudiantes,  
Damos inicio oficial a la Evaluación Parcial N°3, la ponderación más alta de nuestra asignatura (40% de la nota final). Este hito no será una simple continuación de la entrega pasada; el desafío institucional es diseñar, construir y desplegar una solución tecnológica integral (End-to-End) en un contexto laboral real.  
El proyecto consta de dos grandes dimensiones: un Encargo Grupal (10%) que se desarrolla en laboratorio durante 4 semanas, y una Defensa Político-Técnica Individual (30%) con una presentación y demo en vivo de 15 minutos.  
Para abordar con éxito este desafío, la sesión de hoy (Semana 2) es crítica para realizar el Kick-off Ágil y estructurar el mapa de la arquitectura.
🛠️ El Desafío Técnico (Lo que debe incluir el proyecto)
El equipo deberá construir un sistema automatizado que cumpla estrictamente con los siguientes focos:
Pipeline ETL Robusto: Integración de al menos tres fuentes de datos diferentes (ej: el CSV de la Eva 2 + consumo de una API REST externa + una base de datos SQL o NoSQL). Debe incluir validación de esquemas, manejo avanzado de errores y optimización.
Despliegue y Containerización con Docker: Todo el sistema (ETL, Dashboards y APIs) debe estar completamente containerizado usando Dockerfiles, docker-compose y configurado mediante variables de entorno para garantizar su reproducibilidad.
Dashboard Interactivo Multiaudiencia: Desarrollado en Plotly Dash o Streamlit, con interfaces visuales y terminología de negocio diferenciadas según el usuario (ejecutivo, técnico u operativo).
Código Colaborativo y Arquitectura: Estructura modular de carpetas formal (/etl/, /dashboards/, /api/, /docker/, /tests/, /data/), uso profesional de Git (Branching, Pull Requests con revisión de código, control de Issues), e implementación de Testing Automatizado.
📅 Actividad Obligatoria de Hoy: Planificación y Diseño Arquitectónico
Debido a la envergadura del encargo, hoy cada equipo debe trabajar obligatoriamente en el aula en los siguientes entregables:
Paso 1: Asignación de Roles según la Rúbrica:
Líder de Proyecto/Product Owner: Responsable de la documentación técnica, manuales, diagramas de arquitectura y el enfoque de valor de negocio del dashboard.
Data Engineer (Backend/Docker): Responsable del pipeline ETL, la conexión a las 3 fuentes de datos, los scripts de testing y la containerización en Docker.
Data Analyst (Frontend/API): Responsable de la construcción de la API RESTful, el código del Dashboard interactivo y la lógica de visualización multiaudiencia.
Paso 2: Diagrama de Flujo de Datos Inicial: Definir cuáles serán las 3 fuentes de datos que integrarán (retomando su dataset base de la Evaluación 2).
Paso 3: Montaje del Tablero Ágil (Trello/Jira/Miro): Poblar las columnas de tareas con los entregables de la rúbrica (Ej: "Escribir Dockerfile para el dashboard", "Configurar pruebas unitarias en /tests/", "Diseñar vistas del Dashboard para gerencia y operaciones").
📥 Requisito de Salida (Entrega Obligatoria de Hoy en AVA)
Antes de terminar la clase, un integrante por grupo debe subir un documento que contenga:
Arquitectura Propuesta: Breve descripción de las 3 fuentes de datos que integrarán y los componentes del sistema.
Roles Técnicos: Nombre de los integrantes, rol asignado y la justificación técnica de su elección.
Captura del Tablero Digital: Evidencia del Trello/Jira con las tareas iniciales distribuidas y con responsables asignados.
Compromiso Individual: Reflexión breve (un párrafo por estudiante) sobre su responsabilidad de cara a la defensa individual del proyecto.

Estimados y estimadas estudiantes,  
Una vez aprobada la planificación inicial, la asignación de roles y la estructura de sus tableros ágiles, entramos oficialmente en la Etapa 2 del Proyecto Integrador.  
Esta fase es el núcleo de la ingeniería de datos de su solución End-to-End. El objetivo es que dejen atrás el procesamiento manual celda por celda y construyan un flujo automatizado, robusto y profesional utilizando la estructura formal de carpetas exigida (/etl/, /api/, /tests/, /data/).
🛠️ Objetivos Técnicos Obligatorios para esta Etapa
Cada integrante debe ejecutar las tareas asignadas en su rol, pero todo el equipo debe integrarse mediante Git:
1. Robustez del Pipeline ETL (/etl/ y /data/)
Conexión Multifuentas: Escribir los scripts necesarios para extraer datos simultáneamente de las tres fuentes distintas aprobadas en su planificación (CSV original, API externa y base de datos).
Validación de Esquemas: Implementar reglas estrictas en el código para verificar que los datos entrantes cumplen con los tipos de datos y formatos requeridos antes de ser transformados.
Manejo Avanzado de Errores: El pipeline no puede detenerse si encuentra un dato corrupto o un nulo inesperado. Debe capturar las excepciones y registrar eventos mediante un sistema de logging profesional.
2. Desarrollo de la API RESTful (/api/)
Capa Intermedia: Desarrollar los endpoints estructurados que consuman la información limpia desde su base de datos (SQL o NoSQL). Esta API será la encargada de alimentar de forma eficiente al dashboard interactivo en la siguiente etapa.
3. Git Workflow Profesional: Trabajo en Ramas y Pull Requests
Para cumplir con el 15% de la rúbrica sobre uso profesional de Git, la revisión de código ya no es opcional:
Feature Branches: Está estrictamente prohibido programar directamente en la rama principal (main o master). Cada alumno debe crear y trabajar en su propia rama de características (ej: feature/pipeline-etl o feature/api-rest).
Pull Requests (PR) y Revisiones Cruzadas: Para integrar cambios al repositorio principal, se debe abrir un Pull Request. Otro miembro del equipo debe revisar el código, dejar comentarios técnicos y aprobarlo antes de hacer el merge.
Resolución de Conflictos: Deben dejar evidencia en el historial de cómo abordaron y solucionaron los conflictos de código en equipo.
